=== world ===
- world = infinite matrix, coords, can nest
- negative coords ok, origin (0,0)
- world itself = a Container instance
- each cell holds max 1 object/container, or empty
- a Container's inside is ALSO an infinite matrix, not just world
- coords are LOCAL per container (like relative paths, not global)
- entering/opening a container -> always starts at local (0,0)
- exiting/re-entering -> does NOT remember agent's old position inside
  (portal is the deliberate exception, see below)

=== object ===
- object = instance, private state, public functions
  ex: apple.object -> function eat
  basically = class w/ everything private except a public interface
- some public data can shows for an object. see the stand-on object detail mentioned below
- every object has a hash (instance id), separate from type name
  (apple.object = type, hash = which specific one)
- bundles can be downloaded from internet
- NO versioning, NO in-place update of a bundle's code
  -> lifecycle is only: add / remove / move
  (internal state like durability or coin balance still changes via
  the object's own functions -- that's not "versioning")
- objects/items can have durability (limited uses)
- standing on object -> shows basic info (passive)
- `inspect` -> full detail / list of public functions (active)

=== container ===
  Object
  └── Container capability
- container is NOT a separate type, it's an object + in/out capability
- so container can be picked up, dropped, locked... just like any object
  (nothing stops you from carrying off a container unless it's locked)

=== agent ===
- agent = just an outline/pointer at a coord, doesn't occupy a cell
- vision = 16x16, shrinks dynamically if container is smaller, configurable

=== backpack / hand ===
- 1 hand slot (hold 1 object)
- backpack = itself a container (same grid model)
  but permanently attached to agent, not placed in world
  -> access via `backpack open` / `backpack close` (same as container in/out)
- default backpack: scratchpad.object, messager.object, calculator.object
- coin = attached to agent same way backpack is (not a world/backpack item)

=== commands (built-in, minimal) ===
  move <direction> [step]        default step = 1
  container in / container out   must be standing on the container
  pickup                         -> error if hand occupied
  drop [delta]                   default (0,0), among 8 neighbors + self
                                  -> error if no valid spot
  backpack open / backpack close
  object (function args...)      call fn on held object, e.g. object (eat (0.5))
  inspect                        discover what an object supports

- agent talks to it like a terminal, plain text commands, NOT json

=== portal + key ===
- NOT special engine types -- just plain objects w/ a function
- key has one property saves a hash matches its corresponding portal's hash (& vice versa)
- using key -> teleports agent to matching portal
  (this is the intentional exception to "no remembered position")

=== summon ===
- NOT a built-in command -- it's an object (summoner.object) w/ a function
  (keeps core command set minimal, push power into objects)
- addressing, two ideas floated:
    - by position: remember exact coords, or zone + name
    - by area: container name (or bound within one; skip name if area = world) + name
- only works on objects agent already "knows" -- exact definition of "knows"
  still open (seen it? inspected it? picked it up once?)

=== lock ===
- lock = a property/attribute ON the object itself (a struct w/ info)
  NOT a position-based thing
- effect: locked -> can't pickup
- tiers: user / system / agent / ... (how many, not decided)
- current use case = shop ONLY, nothing else yet
- shop needs lock at 2 levels:
    1. the shop container itself (so it can't just be carried off)
    2. each item inside it (so items can't be taken without paying)

=== shop / economy ===
- shop = a container placed in world
  (later: other containers too, e.g. example "house")
- merchant = object inside, unlocks an item (by hash) once paid
- buy stuff w/ coin -- e.g. portal, summoner
- budget for agent is granted by the human user, can be infinite
  -> no in-world agent-to-agent economy right now, just an allowance
- restock policy = user decides, not engine's job

=== broadcast ===
- messager.object = broadcast-able, pings agent on new message
- inbox style, agent can read or ignore
- user messages = highest priority, but STILL just a label
  (ref: iOS notif priority) -- doesn't force agent to read/act
- preview ~255 chars

=== still open / not decided ===
- move/drop param syntax -- literal or just doc shorthand?
- "known object" for summon -- tracked by hash or by type?
- summon/portal: does it MOVE the object/agent or copy it? conflict if
  two agents reference same known object?
- lock tier hierarchy -- does system > user > agent override order hold?
  can one agent's lock be removed by another agent?
- is coin an object (balance(), pay()...) or just a raw number on agent?
- sandboxing for running code from downloaded bundles (untrusted objects)
